# 参考工程 newnew 文档提炼

参考目录：本地开发阶段通过 `.localref/newnew` 软链访问原始资料，不纳入主仓提交。

## 1. 文档中最重要的可迁移思想

### Android 业务架构文档
来源：`docs/android_arch/spec.md`

可迁移点：
- 页面分为待处理、相机/检测、历史案例三类
- 以数据库/案例管理作为业务骨架
- 强调模块职责拆分而不是把所有能力堆在一个页面

### AI 算法文档
来源：`docs/ai_algo/spec.md`

可迁移点：
- 明确了“检测层”和“业务层”应解耦
- 检测只是输入，案件和处置才是完整系统输出
- 掩膜、检测、违规判定是算法链，应该被平台层封装成可展示结果

### 多媒体与云服务文档
来源：`docs/media_cloud/spec.md`

可迁移点：
- 15 秒证据片段是很强的项目展示材料
- 图片、视频、文书应形成统一证据链
- 云端描述生成要和核心归档流程分离

### cases 功能计划
来源：`docs/task_cases_feature/*`

可迁移点：
- 待处理记录 -> 案件归档 是业务闭环的关键
- 车牌聚合、视频裁剪、案例详情页可以直接转译为 Web + Backend 结构

## 2. 当前仓库落地方式

本仓库把这些思想转译为：

- `events`：时序融合得到的违规事件
- `cases`：按车牌聚合后的案件中心
- `clips`：每个案件对应的 15 秒证据片段
- `reports`：正式举报文书文本
- Web 端 + Android 云侧协同模式：共同消费同一后端接口
- Android 端额外保留 `newnew` 迁入后的端侧本地检测模式，用于展示 CameraX / JNI / Room 能力

## 3. 当前已经并入的部分

本轮已从 `newnew` 并入主仓 Android 的能力包括：

- CameraX 实时检测页面
- JNI + ncnn 原生检测链
- HyperLPR3 本地车牌识别
- Room 本地待处理记录 / 案例库
- 本地视频裁剪与本地报告生成

这些能力当前定位为 **端侧演示链**：
- 用于毕设检查时证明“项目具备端侧本地检测能力”；
- 不替代后端主线的事件归档、证据链与举报闭环；
- 与现有 Compose + FastAPI 协同端并存。

## 4. 仍然保留为参考/演进来源的部分

即便已经并入端侧链路，`newnew` 仍有一些内容只作为参考：

- 更大范围的旧工程结构与历史 Windows 构建痕迹
- 原工程文档里未完全落地的 OpenCV 车道掩膜目标
- 旧版网络/云端能力设想

因此当前主仓的准确定义不再是“完全不并入 newnew”，而是：
**已并入可运行的端侧本地链路，但仍以当前 FastAPI + Web + Android 协同闭环为主系统。**
