# 参考工程 newnew 文档提炼

参考目录：本地开发阶段通过 `.localref/newnew` 软链访问原始资料，不纳入主仓提交。

## 1. 文档中最重要的可迁移思想

### Android 业务架构文档
来源：`docs/android_arch/spec.md`

可迁移点：
- 页面分为待处理、相机/检测、历史案例三类
- 以数据库/案例管理作为业务骨架
- 强调模块职责拆分而不是把所有能力堆在一个页面

### AI 算法文档
来源：`docs/ai_algo/spec.md`

可迁移点：
- 明确了“检测层”和“业务层”应解耦
- 检测只是输入，案件和处置才是完整系统输出
- 掩膜、检测、违规判定是算法链，应该被平台层封装成可展示结果

### 多媒体与云服务文档
来源：`docs/media_cloud/spec.md`

可迁移点：
- 15 秒证据片段是很强的项目展示材料
- 图片、视频、文书应形成统一证据链
- 云端描述生成要和核心归档流程分离

### cases 功能计划
来源：`docs/task_cases_feature/*`

可迁移点：
- 待处理记录 -> 案件归档 是业务闭环的关键
- 车牌聚合、视频裁剪、案例详情页可以直接转译为 Web + Backend 结构

## 2. 当前仓库落地方式

本仓库把这些思想转译为：

- `events`：时序融合得到的违规事件
- `cases`：按车牌聚合后的案件中心
- `clips`：每个案件对应的 15 秒证据片段
- `reports`：正式举报文书文本
- Web 端 + Android 端：共同消费同一后端接口

## 3. 没有直接照搬的部分

没有直接并入主系统的部分包括：

- CameraX 实时相机采集
- JNI + ncnn 原生检测链
- HyperLPR Android 本地 SDK
- 旧工程的 Room 本地主数据源模式

原因不是这些没有价值，而是它们更适合作为“参考原型 / 演进来源”，而当前仓库需要优先保证一个能稳定运行、结构清晰、便于扩展的主项目。
